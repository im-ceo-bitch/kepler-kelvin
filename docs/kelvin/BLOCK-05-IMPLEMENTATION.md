## ADR-12 — use canonical Telegram Care instead of another customer agent
The original business repo has `Backend/IumrahBackend/core/telegram/care.js`, `mini-bot.js`, `storage.js`, `telegram_care_threads`, `telegram_care_messages`, existing `careAdmin` and Business UI. `storage.miniEnv` binds DB to canonical BOOKINGS_DB; `mini-bot.handleUpdate` accepts only private user chat, `smartCare` delegates eligible text to `careIncoming`; the original webhook is retained. Existing commands, booking identity, language menu and concierge session remain outside Kelvin's new automation. The unified router gates `/api/internal/kelvin/*` behind core cutover readiness. `kelvinInternal` validates the existing hashed paired-owner token before invoking `/care`; the new control slot binds to exactly one paired owner. No second customer poller or customer transcript database. Three ancillary tables in BOOKINGS_DB: `telegram_care_kelvin_control` (opt-in owner + watermark), `telegram_care_kelvin_notices` (at-most-once notification claims/delivery state), `telegram_care_kelvin_audit` (requested owner actions, metadata only). Existing canonical messages record actual replies and delivery. Audit table currently records attempts, not a complete immutable security audit; existing Business-side mode switches are not separately mirrored in that table.

Default off. After staging and approval, `/biz enable` on the existing private Kelvin bot enables the adapter, checks configured iumrah Telegram token, and sets the notification watermark to the latest canonical message ID. No old-message flood on first enable or re-enable. `/biz disable` returns Care to its original reply policy; it does NOT disable Care itself, reset dialog modes or delete existing history. Disable before revoking pairing or changing owner; revoking the pairing blocks bridge access but does not automatically change the persisted Care policy. A different paired owner cannot take over the configured slot. Owner reassignment needs an explicit administrative procedure, not provided by this patch. Existing iumrah customer token stays in backend; existing Kelvin owner token stays on Mac. Old local `business.sqlite3` and `business.py` retained as historical code/tests, not invoked by current runtime. No migration or replay of that separate inbox. `connect.sh business` now directs user to canonical Care instead of starting another customer bot.

## ADR-13 — grounded bounded response and customer isolation
Enabled Care uses the existing approved localized service copy and conservative intent recognition (RU, UZ Latin, UZ Cyrillic, EN fallback). Greetings, thanks, general questions about service, tickets, hotels, transfer, guidance and booking instructions use fixed copy. Price flow extracts city/date or month/party size from the current message, and for an explicit follow-up from up to eight recent same-thread user messages (30 minutes, bounded from last recognized price question). Ask only missing recognized slots; a complete query goes to staff for live price verification. Unknown/multiple incompatible topics, payment/refund/discount/guarantee, sensitive messages, injection-like requests and explicit manager requests transfer to staff. Some multi-topic questions containing price prioritize price. Exact inventory, live quotes, nuanced Uzbek morphology, arbitrary conversational intent, relative dates, corrections and full multi-turn semantic context remain limited; do not claim fully generative customer assistant. No new Claude/Gemini/Ollama calls for enabled client responses. Existing approved Care copy is the source, not a live pricing engine; production service text must be reviewed by owner. Price, availability, booking state and payment cannot be invented or mutated. Personal booking/concierge paths continue original logic. No customer messages enter the private owner agent/model or its typed memory. Customer data remains in canonical thread; sensitive recognized input replaced before storage, secondary notice/history redaction for common tokens, phone/email/links. Pattern redaction is not comprehensive PII detection. Only private owner receives limited excerpts via explicit bridge; no new external model data processing. Customer text cannot call a tool.

## ADR-14 — handoff, notifications, delivery
`care-kelvin.js` reserves auto/staff send atomically against the canonical thread mode and any existing `sending` row. Owner take/resume/staff reply returns 409 while a send is in flight. Once a confirmed staff takeover has changed mode, no new automated Care send is reserved until resume. A reply uses canonical `careAdmin` and existing customer bot, stable idempotency key derived from owner Telegram message event, thread and owner; an explicit different message event is a new operation. Duplicate staff request cannot send twice. Existing legacy responder now uses the same reservation guard. On failed/unknown Telegram delivery, mark `uncertain`, pause automatic replies, and do not retry blindly. Stale sending after 120 seconds is quarantined. An already dispatched external network call cannot be recalled; a customer-triggered handoff/legacy concierge response may overlap with a previously dispatched message. Simultaneous customer messages can leave a later message without auto-response if a send is already reserved; it is visible in canonical history and notification queue, not silently retried.

Owner notification candidate derived from canonical user + `reply:<external_id>` rows. Meaningful sent responses include customer question, actual recorded answer and current dialog mode; no confirmed delivery claim if uncertain. Human-mode inbound messages can generate notification without an automatic answer. Simple courtesy messages in auto mode are suppressed. Claim is persisted before sending, one notification per canonical user message. On loss of acknowledgement or transport failure, store/expire to uncertain; no automatic resend, so at-most-once attempted delivery rather than guaranteed delivery. Older pending events are inspectable in canonical history. One notification per active polling cycle (~20s plus I/O, 60s disabled), no voice duplicate or technical reports. For Mac sleep, notifications wait until restart; enabled canonical Care replies continue on existing Cloudflare backend independently of Mac (subject to backend availability and quotas). Pending notices since activation may accumulate; no exact delivery-time guarantee or capacity benchmark. On uncertain notice, inspect Care manually. Uncertain status visible in `/biz status`; no retry UI yet.

Private owner controls: `/biz status`, `/biz enable`, `/biz disable`, `/biz pending`, `/biz take ID`, `/biz resume ID`, `/biz show ID`, `/biz reply ID текст`. New buttons use `care:take|resume|show:<thread>` and existing private Telegram user authorization. After take, the reply command is supplied; staff can also use existing iumrah Business Care UI with same canonical mode and history. Old `biz:*` buttons intentionally not routed to new thread IDs. No change to owner natural dialogue, shared memory, autonomy or voice. Previous OpenJarvis SystemBuilder/JarvisSystem/Orchestrator, scheduler, evidence and strategic analysis retained, no new upstream agent required for the communication adapter. No modifications to upstream `src/openjarvis`, iOS, workflows or unpackers.
